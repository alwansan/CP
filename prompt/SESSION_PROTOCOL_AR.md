# بروتوكول الجلسات والتسليم — Cinemana Pro

**فرع الكتابة لهذا العمل:** `experiment/rea-source-recovery`. هذا البروتوكول مستوحى من آلية Raft؛ لكنه لا ينشئ عمالاً أو مهاماً مجدولة تلقائياً.

## بداية جلسة جديدة
1. اقرأ `AGENTS.md` → `memory/MEMORY.md` → `memory/STATE.json` → أحدث جلسة في `memory/sessions/`.
2. تحقق من HEAD الحي والـCI والـCL. لا تعتمد على تاريخ ملف الذاكرة لتقرير آخر نتيجة؛ سجّل HEAD المقروء.
3. اقرأ تقارير `recovery/` المتعلقة بمشكلة المالك؛ قارِن معلومة الجلسة السابقة بنتيجة الاختبارات الحية.
4. أنشئ `memory/sessions/YYYY-MM-DD_<unique-session-id>.md`. يحتوي دائماً:
   - `session_id`, `origin=chat|schedule`, التاريخ والمنطقة الزمنية أو UTC، الفرع، HEAD قبل العمل؛
   - هدف المالك، نطاق مسموح/ممنوع، والأدلة؛
   - الملفات التي تغيّرت، commit SHA إن وجد، الاختبارات وروابط Actions وحالتها؛
   - النتيجة الصادقة: `verified` أو `diagnostic only` أو `blocked` أو `hypothesis`؛
   - المتبقي والخطوة التالية التي يستطيع عميل جديد تنفيذها بدون تخمين.
5. حدّث `memory/MEMORY.md` عند تغير معرفة مهمة و`memory/STATE.json` عند تغير الحالة/الهدف. لا تمسح تاريخ النتائج السلبية.

## ترتيب الأدلة
1. إعادة إنتاج على هاتف المالك مع سجل وإصدار ووقت.
2. اختبارات Android فعلية مع آثار وسجلات مؤكدة.
3. CI ناجح على SHA معروف واسم workflow.
4. اختبارات Java أو فحوص المصدر المقروءة.
5. استنتاج أو فرضية من ذاكرة سابقة (تُوسم فرضية).

**مثال:** `smoke APK built` لا يعادل `smoke APK launched`، وكلاهما لا يعادل `Cinemana Pro production working`.

## حماية العمل والتوازي
- لا تعدّل الفروع الأخرى ولا تدمجها ولا force-push.
- عند حدوث تغير في HEAD أثناء التنفيذ: حدّث معلوماتك وراجع التعارض، ولا تكتب فوق تغيير الآخرين.
- لكل جلسة ملف منفصل؛ لا تعدّل سجل جلسة عميل آخر. يمكن تحديث ملف MEMORY المشترك بعد مراجعة أحدث نسخة.
- لا تبدأ اختبارات مدمرة؛ لا تفتح قواعد بيانات مستخدم حقيقية لاختبار ترحيل Room.
- نظّف السجلات من الروابط الموقعة، رموز الدخول، البيانات الخاصة قبل أي نشر عام.

## عند وصول ملف سجل جديد
- افحص المسار المعطى في CL فعلياً، وتاريخ الملف وحجمه ونوعه قبل استنتاج وجود المحتوى.
- وثّق سيناريو الفشل وزمن البداية والنهاية والحزمة والتثبيت والـSHA.
- اعزل الأعراض بين: `Downloads/MKV`، `Room`، `Player/FFmpeg/Surface`، `UI/Search`، `Account`، `Crash/Performance`.
- اكتب فرضيات قابلة للتفنيد واختباراً صغيراً آمناً قبل التعديل.

## نهاية الجولة
حدّث ملف الجلسة والحالة ثم اذكر للمستخدم روابط الملفات التي تغيرت والـSHA والنتيجة وماذا يتطلب اختبار الهاتف. إذا لم تُشغَّل اختبارات، قل ذلك صراحةً.
