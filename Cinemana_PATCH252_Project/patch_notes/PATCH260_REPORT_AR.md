# PATCH260 — كبسولة الاسترداد داخل MP4 وMKV

## الهدف

تقليل اعتماد إصلاح التنزيل والتحويل على سلامة مجلدات `data/` و`log/` وحدها. يحمل كل ملف مكتمل كبسولة JSON ذات إصدار معروف، وتبقى نسخة جانبية أثناء مراحل المعالجة حتى يستطيع النظام استعادتها إذا تعذّر فتح الحاوية أو إعادة تغليفها.

## أين تُحفظ المعلومات؟

- **MP4:** حقول حاوية مخصصة مثل `cnm_recovery_format` و`cnm_recovery_token` و`cnm_recovery_manifest_b64`، وتُكتب بإعادة تغليف تدفقية من دون إعادة ترميز الصوت أو الفيديو.
- **MKV:** مرفق JSON باسم `cnm_recovery.json` من نوع `application/json`، مع حقول تعرّف تنسيق الاسترداد ورمز المحتوى.
- **نسخة جانبية مؤقتة:** `Cinemana/work/data/cnm_recovery/<token>.json`. تسمح بمتابعة الاسترداد إذا كان الملف جزئيًا أو رفض FFmpeg تعديل الحاوية.
- **علامة تحقق محلية:** ملف `.mp4state` مرتبط بحجم الفيديو ووقت تعديله، وبحجم JSON الجانبي ووقت تعديله. لا يُعاد التغليف إذا تطابقت البصمة المحلية؛ وإذا تغيرت البيانات يُعاد فحصها.

## محتويات الكبسولة

تُسجل الكبسولة، بحسب المرحلة وتوفر البيانات، رمز الحلقة ومعرّف عنصر التنزيل ومعرّف المهمة، العنوان والموسم ورقم الحلقة ونوعها والجودة، مسار MP4 واسمه وحجمه ووقت تعديله، المسار المقصود لـ MKV والمسار النهائي بعد الترتيب، الطابع الزمني والمرحلة الحالية، رابط الفيديو المحفوظ إن توفر، مصادر الترجمات البعيدة وصيغها ومعرّفاتها، ومسارات ملفات الترجمة المحلية مع أحجامها وأوقات تعديلها وبصمات SHA-256.

وتحمل كذلك إرشادات استرداد صريحة: التحقق من هوية الملف قبل ربطه بصف قاعدة البيانات، التأكد من دعم خادم التنزيل لاستكمال النطاقات قبل استئناف بايتات قديمة، تحديث الروابط الموقعة أو المؤقتة قبل استعمالها، والتحقق من خطة الترجمات قبل بدء التحويل.

## دورة العمل

1. عند قبول مهمة التنزيل تُنشأ كبسولة أولية تحفظ هوية المهمة ورابط المصدر المتوقع.
2. بعد إيصال اكتمال التنزيل والتحقق من المسار والحجم، تُحدّث الكبسولة ثم يحاول النظام إدخالها في MP4.
3. إذا تعذر التضمين في تلك اللحظة، تبقى النسخة الجانبية معلّمة بأن التضمين لم يكتمل. يُعاد فحص ملفات MP4 المكتملة عند مرور ماسح الإصلاح، بدل افتراض أن المحاولة الأولى نجحت.
4. قبل تحويل MP4 إلى MKV تُحدّث بيانات المرحلة والمسار الهدف وتُضمّن نسخة JSON في MKV.
5. بعد إنتاج MKV النهائي يحاول النظام تسجيل المسار النهائي في قاعدة البيانات والتحقق منه، ثم يحدّث الكبسولة والمرفق داخل MKV بالمسار النهائي.
6. لا يسمح مسار التنظيف بحذف MP4 أو ملفات الترجمة إذا فشل تحديث الكبسولة النهائية أو لم تؤكد قاعدة البيانات المسار النهائي وحجم الملف. وعند فشل إعادة تغليف MKV تُستعاد نسخة JSON الجانبية السابقة قدر الإمكان.

## قيود وأمان

- وجود رابط داخل الكبسولة **لا يضمن** أنه سيظل صالحًا؛ فقد ينتهي توقيع الرابط أو تتغير صلاحيات الوصول. ينبغي تحديث المصدر من التطبيق قبل محاولة الاستئناف، وعدم اعتبار رابط قديم تصريحًا دائمًا.
- قد تحتوي روابط التنزيل أو الترجمة على رموز وصول أو بيانات اعتماد مؤقتة. لذلك لا ترفع ملفات MP4/MKV الحاوية على روابط إلى مستودعات عامة ولا تشاركها قبل مراجعة محتواها.
- تُسجل بصمة SHA-256 للترجمات المحلية لمساعدة النظام على كشف استبدال ملف ترجمة بملف آخر يحمل الاسم نفسه. لا تُعد البصمة بديلًا عن مطابقة رمز الحلقة وخطة الترجمات.
- إدخال البيانات يزيد حجم الحاوية قليلًا. عند نجاح تضمين MP4 يُحدّث إيصال التنزيل المحفوظ بالحجم الفعلي الجديد، بينما يبقى حجم المصدر قبل التضمين داخل الكبسولة للمقارنة.
- يعتمد الاسترداد من داخل الحاوية على وجود FFmpeg ودعم صيغة الحاوية للبيانات أو المرفقات. تبقى النسخة الجانبية هي مسار الرجوع عند غياب ذلك.

## حالة التحقق

أُضيفت فحوص ثابتة في سير عمل GitHub Actions للتأكد من وصل نقاط التضمين والاسترداد والتحقق من قاعدة البيانات. مراجعة النص المصدر لا تعادل بناء APK أو اختباره على الجهاز؛ يلزم أن ينجح بناء GitHub Actions ثم تُختبر دورة تنزيل مكتمل، وتضمين MP4، والتحويل إلى MKV، وتحديث المسار النهائي، واسترداد الكبسولة بعد إزالة نسخة البيانات الجانبية على نسخة اختبارية قبل اعتمادها للاستخدام اليومي.
