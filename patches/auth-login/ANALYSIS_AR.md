# تشخيص تسجيل دخول سينمانا — 2026-10-28

فرع العمل: `fix/auth-login-diagnostics`، مشتق من `fix/download-mkv-self-repair` عند `06ec99add982ace4b35898f763b31ec532a5a7e5` (PATCH265).

## ما ثبت من المرفقات

تمت قراءة الجلسات المشتركة الثلاث كاملة بالنص المعروض. الأولى تخص Google وإعدادات PATCH240/242؛ الثانية تخص تقرير VirusTotal لتطبيق Reezn وليست دليلاً على مشكلة سينمانا؛ الثالثة خطة تشخيص PATCH244 توقفت قبل بناء APK. الكلام عن تجهيز اللوق في تلك الجلسة لا يعني أنه موجود في هذا الفرع.

تم تحليل ملفي HAR محلياً دون إعادة إرسال أي طلب أو استعمال رموزهما. الأول 131 إدخالاً والثاني 224. كلاهما يحتوي حركة متصفح Opera؛ لا يحتويان طلب تطبيق إلى `core/connect/google` أو `core/connect/token` ولا طلب تبادل Google إلى `/oauth2/v4/token`.

| الاختبار | الدليل | الاستنتاج |
|---|---|---|
| فتح حساب `.cc` | صفحة الدخول HTTP 200 وطلب externallogin HTTP 302 | النطاق كان قابلاً للوصول في وقت الالتقاط |
| Google عبر `.cc` | redirect_uri هو `https://account.shabakaty.cc/core/signin-google` ثم صفحة خطأ Google؛ الصورة تعرض `400 redirect_uri_mismatch` | Google رفض إعداد عنوان الرجوع؛ ليس دليلاً على حظر DNS أو الشبكة |
| Google عبر `.com` | نفس Web client_id في الالتقاطين، callback على `.com`؛ رجوع `/core/signin-google` ثم `/core/` HTTP 200 | يتوافق مع نجاح دخول المتصفح الذي أبلغ به المستخدم وأظهرته الصورة |
| Google داخل APK | لا توجد حركة التطبيق في هذين الملفين | لا يمكن حسم فشل النسخة الأصلية أو المعدلة من HAR المتصفح وحده |

الفرق بين مساري المتصفح هو نطاق callback مع نفس Web client_id. لا يمكن مشاهدة قائمة Google Cloud المسموح بها من هذه الملفات، لكن الخطأ يثبت رفض callback المرسل. لا ننشر client_id أو الحساب أو الكوكيز في التقرير.

اختبار خارجي غير موثّق بهوية على مسار discovery أعاد `.com` HTML 200 وليس JSON و`.cc` HTTP 503 من بيئة البحث؛ لا يثبت صلاحية API التطبيق ولا يصف اتصال المستخدم. يجب اختبار API من الهاتف باللوق.

## ما ثبت من المصدر

- `app/smali/com/shabakaty/downloader/s30.smali`: عنوان خدمة الحساب كان `.cc`؛ ينشئ ClientInformation الخاص بالمحمول.
- `app/smali/com/shabakaty/usermanagement/utils/externalLogin/GoogleLogin.smali`: يستعمل Google Play Services ثم يبادل server authorization code عند `https://www.googleapis.com/oauth2/v4/token` مع redirect_uri فارغ. هذا مسار مختلف عن callback الويب. لا تنسخ callback المتصفح إليه.
- Google client_id في التطبيق مختلف عن Web client_id الظاهر في HAR؛ اختلافهما ليس وحده خطأ، فهما عميلان لتكاملين مختلفين.
- catch الخاص بـ Google ApiException كان يطبع stack trace ثم يعود دون onGoogleLoginFail. هذا خلل واضح في إنهاء المحاولة؛ قد يترك الواجهة تنتظر عند فشل Google. لا يثبت السبب الذي جعل Google يفشل ابتداءً.
- callback تبادل الرمز كان يقرأ optString(access_token) ويدعو النجاح حتى لو رجع JSON خطأ أو رمز فارغ، دون التحقق من HTTP.
- `UserManagementApi.smali`: حسابات التطبيق تستخدم `core/connect/token` و`core/connect/google` و`core/connect/userinfo`، بينما تسجيل المتصفح ينشئ جلسة Cookie. جلسة الموقع ليست تلقائياً جلسة API للتطبيق.

## التغييرات في هذا الفرع

1. تحويل عنوان حسابات التطبيق فقط إلى `https://account.shabakaty.com/`. هذه تجربة مبنية على نجاح المتصفح، وليست إثباتاً بأن backend المحمول يقبل النطاق. نطاقات الفيديو والتنزيل لا تتغير.
2. تسجيل حالات Google الرقمية ومعالجة الفشل عبر callback الموجود بدلاً من ابتلاع الاستثناء. معالجة غياب authorization code كذلك.
3. رفض HTTP خارج 2xx وaccess_token المفقود أو الفارغ قبل إرسال النجاح. لا ننقل رموزاً فارغة إلى خدمة حسابات شبكتي.
4. AuthTrace يسجل بدء Google وعودة النتيجة ووجود الرمز والنتيجة النهائية. نقطة OkHttp المشتركة تسجل الطلب/الرد أو صنف IOException، وتشمل الاستدعاءات المتزامنة وغير المتزامنة للمضيفين المحددين فقط.
5. إزالة طباعة TokenResponse من مساري login/refresh القديمة؛ كانت قادرة على كشف الرموز في logcat. هذا ليس تدقيق خصوصية شامل لبقية التطبيق.
6. أداة تحليل HAR محلية تعتمد قائمة سماح وتستبعد bodies وheaders وجميع قيم query الحساسة. لا تُرفع ملفات المستخدم إلى git.

لم يتم تغيير OAuth secrets أو client IDs أو Firebase أو التوقيع أو issuer أو تعطيل TLS، ولم تتم إضافة إعادة محاولات تلقائية أو fallback ينقل بيانات الاعتماد بين نطاقين.

## قراءة اللوق واختبار الهاتف

فعّل اللوق الموجود بالتطبيق. أحداث AUTH تصل إلى `Cinemana/work/log/ui95.log` في التخزين المشترك؛ عند تعذر الكتابة يستخدم اللوق الحالي `files/log/ui95.log` داخل التطبيق. وتظهر أيضاً في logcat تحت `CinemanaAuth`. تحترم الأحداث مفتاح إيقاف اللوق الحالي، وتستخدم عامل الكتابة الحالي دون خيوط جديدة أو قراءة أجسام HTTP. أحداث AUTH لا تمر بفلتر إسقاط الأحداث المتكررة خلال ثانيتين.

اختبر على الشبكة نفسها دون تغيير DNS أو VPN أثناء المقارنة:

1. دخول Google على موقع `.com` للتحقق من بقاء الحالة المعروفة.
2. نسخة تشخيصية مبنية من هذا الفرع: محاولة Google واحدة وانتظار ظهور نتيجة أو خطأ، ثم محاولة اسم المستخدم وكلمة المرور إذا كانت متاحة للحساب.
3. اجمع أسطر AUTH مع الوقت. لا ترسل HAR الخام أو cookies أو passwords أو tokens. رمز `call` يربط بداية طلب HTTP بنهايته؛ المدة تُحسب من أوقات السجل.
4. قارن بالنسخة الأصلية الحديثة مع توثيق مصدرها ورقمها، دون إزالة تطبيق يحوي تنزيلات لمجرد الاختبار.

| آخر دليل في السجل | ما يعنيه |
|---|---|
| google_signin_begin فقط | لم يصل معالج نتيجة Google بعد؛ يحتاج فحص Activity/Play Services والإلغاء |
| google_signin_error status=10 | إعداد هوية تطبيق Google غير صحيح عادةً؛ تحقق من الحزمة وSHA-1 وعميل OAuth لدى مالكه |
| google_account_result_ok ثم google_authorization_code_missing | نتيجة Google وصلت لكن لا يوجد رمز تبادل صالح |
| request_begin إلى google_token ثم http_response غير 2xx | وصل رد لطلب تبادل Google؛ يحتاج تشخيص إعداد العميل/الرمز من جهة المالك |
| google_token_present ثم طلب /core/connect/google | وصلت المصادقة إلى مرحلة حسابات شبكتي |
| request_begin ثم UnknownHostException/SSLHandshakeException/SocketTimeoutException | فشل نقل/اسم نطاق/شهادة/مهلة حسب الصنف؛ ليس رفض كلمة مرور |
| http_response إلى شبكتي ثم login_result_failed | وصل رد HTTP لكن الدخول لم يكتمل؛ الحالة النهائية مهمة |
| login_result_success | التطبيق أعلن اكتمال الدخول؛ يلزم التحقق من الحساب داخل الواجهة |

`request_begin` يعني أن عميل الشبكة بدأ التنفيذ، ولا يثبت أن الحزمة وصلت للخادم. الرد HTTP يثبت أن العميل استلم استجابة؛ لا يثبت وصول الطلب للأصل بدلاً من وسيط أو cache ولا يثبت نجاح الدخول. غياب الرد وحده لا يثبت أن الخادم لم يستلم الطلب. اللوق لا يراقب Google Play Services من الداخل أو المتصفح الخارجي ولا يفرض مهلة UI شاملة.

## تغيير Google أو الانتقال إلى المتصفح

Google توثّق ضرورة التطابق الحرفي لعنوان الرجوع مع العميل المسجل. يستطيع مالك مشروع Google الخاص بموقع شبكتي إضافة callback الصحيح للنطاق المطلوب وتوحيده مع إعداد الخادم. تعديل APK لا يغيّر قائمة السماح عند Google.

لهوية Android يلزم تسجيل اسم الحزمة الفعلي وSHA-1 لشهادة النسخة النهائية في مشروع Google المناسب. النسخة المعدلة باسم حزمة/توقيع مختلف قد تفشل حتى إن كان backend سليماً. لكن ظهور المشكلة في نسخة أصلية أيضاً يمنع اعتبار توقيع النسخة المعدلة التفسير الوحيد.

إنشاء مشروع Google خاص وعميل Android + Web لا يضمن قبول خادم شبكتي للرمز. يلزم تكامل مدعوم مع الخادم وموافقته على العميل والجمهور/المزود. أسرار الويب يجب أن تكون في خادم مملوك للمطور، لا داخل APK. لن نستبدل المفاتيح عشوائياً أو نستعمل عميل الموقع بدلاً من عميل الهاتف.

المسار الأنسب مستقبلاً إذا كان الخادم يدعمه: Custom Tabs أو متصفح النظام، Authorization Code مع PKCE وstate، وcallback مسجل يعيد جلسة تطبيق مصرحاً بها. فتح صفحة الحساب وحده أو نسخ Cookie المتصفح لا يحقق ذلك. لا توجد في المرفقات مواصفة تثبت دعم هذا الربط.

## التحقق وحدوده

بناء Apktool الكامل نجح محلياً، مع اختبارات المشروع للتحقق من recovery والمراجع وتدفقه، وثلاثة اختبارات لأداة HAR تشمل منع تسريب القيم الحساسة. لا توجد بيئة Android فعلية لإثبات ART verification أو نجاح Google أو UI؛ نجاح تجميع Smali لا يساوي نجاح التشغيل.

هذا فرع تشخيص وإصلاح معالجة الخطأ، وليس إعلاناً بأن تسجيل الدخول أصلح على الهاتف. لم يُعدّل main أو فرع الأساس، ولم تُنشر ملفات HAR أو جلسات الحساب.
