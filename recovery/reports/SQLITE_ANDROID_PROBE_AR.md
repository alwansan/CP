# اختبار استعادة تنزيلات MKV داخل SQLite الفعلية على Android

الفرع التجريبي: `experiment/rea-source-recovery` — 29 أكتوبر 2026.

## المشكلة التي يعالجها التغيير

في نموذج الترحيل السابق كان `restoreDownload` يحتفظ بمسار الملف فقط، لكنه لا يحتفظ بالحجم الأصلي. وكان من الممكن أيضاً اعتبار عملية الاستعادة ناجحة إذا أكمل الـDAO عملية `UPDATE` دون استثناء، حتى لو لم تتغير أي سجلات.

## ما الذي تغير فعلياً؟

داخل `modernized/core-downloads`:

- أضفنا `DownloadRow.originalBytes` إلى لقطة السجل السابقة. الدالة العامة القديمة ذات ثلاثة معاملات باقية لأغراض التوافق، وتُرجع `-1` كحجم غير معروف.
- `MkvPromotionCoordinator.promote` يرفض أي عملية كتابة عندما يكون الحجم الأصلي غير معروف؛ كي لا تكون الاستعادة لاحقاً ناقصة.
- أضفنا إلى `Port` دالة `verifyRestored(...)` لإعادة قراءة قيم التنزيل وملف سينمانا والترجمات بعد محاولة التعويض.
- عند وجود فشل تعويض أو عدم تطابق في إعادة القراءة، ترجع `ROLLBACK_FAILED`، وليس `ROLLED_BACK`.
- اختبارات Java تغطي الاسترجاع الصامت الذي يتجاهل تحديث السجل، خطأ إعادة القراءة، فشل واحد من أوامر الاسترجاع الثلاثة، واسترجاع الحجم السابق.

**اختبارات Java المؤكدة:** 75 حالة للـCoordinator، و19 حالة للـPreflight، و41 لمنطق البحث، و34 فحصاً لربط XML. سجلها:
https://github.com/alwansan/CP/actions/runs/40936771126

## فحص Android SQLite الحقيقي، وليس قاعدة وهمية

داخل `modernized/android-smoke/SqlitePromotionProbe.java` توجد قاعدة `SQLiteDatabase.create(null)` جديدة **في الذاكرة** مع ثلاثة جداول تشخيصية:

- `diag_downloads` (هوية المهمة والملف والحجم).
- `diag_cinemana` (ربط الفيلم أو الحلقة بمهمة التنزيل).
- `diag_subtitles` (مسار الترجمة).

يستخدم الاختبار أوامر `CREATE TABLE` و`INSERT` و`UPDATE` و`SELECT` الحقيقية داخل Android. ويغطي ست حالات: نجاح الترقية، وفشل التحديث بعد كتابة Downloads، وفشل الكتابة بعد تحديث Cinemana، وفشل الكتابة بعد تحديث Subtitles، وفشل قراءة ما بعد الكتابة، ومحاكاة نجاح وهمي لاسترجاع سجل Downloads.

تظهر النتيجة في شاشة تطبيق التشخيص تحت `SQLite rollback readback`، واختبار المحاكي لا ينجح إلا إن ظهرت `PASS (6 in-memory SQLite cases)`.

**ملاحظة مهمة:** التجربة لا تستعمل قواعد سينمانا الأصلية أو حساب المستخدم أو مساحة ملفات التنزيل. تُنشأ كل قاعدة مؤقتة داخل الذاكرة وتُغلق بعد حالة الاختبار. وهي لا تختبر انقطاع الكهرباء أو موت العملية أو استرجاعها من القرص بعد إعادة التشغيل؛ ذلك يتطلب Journal دائم وربط DAOs الأصلي. لذلك لا يجوز اعتبار هذا بديلًا جاهزاً لـ`MkvExporter.promoteDatabase` الأصلية.

## حدود الأمان والفروع

- جميع الملفات داخل `experiment/rea-source-recovery` فقط.
- لا دمج إلى `main` ولا تعديل في `feature/local-account`.
- APK التشخيصي يحمل اسم حزمة منفصلاً، وليس سينمانا الحقيقي.
