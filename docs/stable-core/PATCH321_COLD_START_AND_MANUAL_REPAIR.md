## Confirmed recovery design in source
- `CinemanaApplication.onCreate` invokes `Restart108.bootstrap`, then `DownloadRepair129.startup`. `Restart108.bootstrap` already uses `Restart108.main(Context)` to avoid starting native resume in `:filedownloader`.
- **Defect 1:** `DownloadRepair129.startup` previously started `MkvRepairStartup` on **every process**, including the manifest's separate `:filedownloader` service. Each process owns separate static singleton scheduler, observer, ACTIVE_JOB_KEYS and FFmpeg permit; could cause two competing independently constrained mux queues. Gate using same known `Restart108.main` process detection; downloader service keeps network downloading.
- **Defect 2:** `MkvRepairStartup.run` slept **8 seconds before its first recovery scan**, reducing ability to restore finalized orphan MP4s after user force-stop/reopen. PATCH321 runs the **existing guarded DownloadRepair129.execute()** immediately on its **background thread**; retains the 8s *second* pass to retry database/manifest/subtitle readiness, calls `RecoveryCapsule.recoverPending`, and scans the native queue when sidecar recovery actually returns a positive count. Always request one new coalesced audit after delayed sidecar pass. Record stage markers `PATCH321_BOOT_IMMEDIATE_AUDIT` and `PATCH321_BOOT_DELAYED_RETRY` in `Cinemana/work/log/download_repair_actions.log`.
- **Defect 3:** manual Repair Downloads worker previously ran only `DownloadRepair129.execute`, not the startup sidecar recovery. PATCH321 manual worker calls `RecoveryCapsule.recoverPending`; calls `Queue110.scan` if there were recovered sidecars; **then** runs original `DownloadRepair129.execute` with strict source verification. It is a worker thread, not UI thread. Existing RUNNING gate avoids duplicate manual starts.
- **Defect 4:** `MkvReconciler$Audit.run` silently swallowed Throwable on an audit; PATCH321 adds `MkvReconciler.auditFailure(Throwable)`, recording only exception class `MKV_AUDIT_FAILURE_CLASS=...` into `download_repair_unresolved.log`, never URL/path/message. It calls `auditFinished` afterwards so outstanding work can retry at the existing 1.5-second audit cadence.

## Preserved invariants
- The auditor watches final MP4 and subtitle events with FileObserver and re-scans oldest-first with `MkvRepairAgeComparator` and an 8-candidate pass limit; the FIFO MKV executor still has **1 worker**, 1 FFmpeg permit and `ACTIVE_JOB_KEYS` de-duplication.
- `Queue110.mayRepairCompleted` protects paused/active/deleted native tasks. `Inputs114.verified` and `MkvManifestStore` protect exact expected subtitle count, identity and filesystem. The source MP4 stays intact unless a final verified MKV is promoted through DB and disk gates. No mass clean/delete action; do not modify `work/data` or prior downloaded media.
- After Android **Force stop**, no threads, observers or FFmpeg process can continue running. The next *manual app open* starts recovery from persistent sidecars, completion receipts and on-disk MP4s. An interrupted FFmpeg remux restarts from the intact source; it does not resume FFmpeg's output at the exact same byte offset. Network partial resumption is constrained by the old downloader's verified state and HTTP server range support; do not promise bit-perfect resumability of every source.
- No change to `main`, only `feature/stable-core-ui-performance`. Full protected CI Smali/DEX, regression and signed direct APK required.
