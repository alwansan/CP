## PATCH329 technical change
`MkvExporter.onRecoveredVideo(context, item, file)` previously:
1. Validated `Queue110.mayRepairCompleted`, actual MP4 file, correct extension, and deduped by jobKey under JOB_LOCK.
2. Created `MkvExporter$Recovered`, then synchronously wrote `MkvStateStore.setBusy(..., "QUEUED")`, **inside the outer catchall**.
3. If that *nonessential UI/status write* threw, the outer catchall removed `ACTIVE_JOB_KEYS` without ever submitting the validated remux; a second `setBusy(..., "FAILED")` could also throw before the original error was logged. This source-confirmed failure mode was not addressed by PATCH327, which protected the *normal completion* path, not the recovered queue.
4. PATCH329 **only catches Throwable around the initial recovered `QUEUED` state write**, records a Logcat `PATCH329_RECOVERED_QUEUE_STATE_WRITE_FAILED_CONTINUING` marker, then submits the same original Runnable once. The outer `JOB_LOCK` catchall and dedupe rollback still apply to real executor/enqueue exceptions. During rollback, optional `FAILED` state-write errors are contained so original `RECOVERED_ENQUEUE_FAILED` is still captured by `DownloadRepair129.recordThrowable`. No task duplication or relaxed file checks.
5. `scripts/test_patch329_recovered_enqueue_resilience.py` asserts the ordered Smali catch ranges, mandatory handler-first `move-exception`, safe forward `goto`, serialized key lifecycle, exactly-one execute, rollback original-error preservation and absence of any source deletion. The same tests are in the protected CI gate; Release tag/name/file now `PATCH329`. Must validate actual CI and fresh on-device installation before claiming functionality.
