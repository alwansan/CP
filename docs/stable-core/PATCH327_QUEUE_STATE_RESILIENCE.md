## Identified vulnerable flow and PATCH327 change
1. In `MkvExporter.onVideoCompleted`, `ACTIVE_JOB_KEYS.add(key)` succeeded **before** the `MkvStateStore.setBusy(...QUEUED)` call, while submission to `JOB_EXECUTOR.execute` happened **after** the busy-state write. If that write threw (Room/UI persistence transient failure), an active dedupe key could remain without its Runnable ever joining the queue. This is a *source-level failure possibility*, not established as the historical E42/E49 root cause.
2. In `MkvExporter.runRecovered`, `MkvStateStore.setBusy(...IDLE)` occurred **before** `ACTIVE_JOB_KEYS.remove(key)`, so a failure during worker cleanup could also leave the key stranded and prevent future retry.
3. PATCH327 catches those specific busy-state writes, logs concise `QUEUE_STATE_WRITE_FAILED_CONTINUING` / `RECOVERED_IDLE_UPDATE_FAILED_CONTINUING` warnings, and proceeds respectively to actual submission or key release. The guarded source/subtitle/Room/native completion/Lease115 conversion path is unchanged. Each catch handler has an explicit normal-path `goto` to avoid the Android ART `Can flow through to move-exception` verifier regression from PATCH321.
4. The recovered worker now emits `QUEUE_START recovered key=<job-key>` (the old `PATCH319_EXPORT_JOB_START` had no key), making per-item queue start and liveness traceable without exposing signed download URLs.
5. The change does **not** alter the one-worker executor, single FFmpeg permit, native download concurrency, original MP4s, subtitles, sidecars, app data, persistent Room rows or final MKV publication. No scanning or stage deletion was added to this patch.
