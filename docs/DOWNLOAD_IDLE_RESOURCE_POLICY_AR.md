## Proposed demand-driven work states
Treat each subsystem independently; multiple active roles can coexist. Global summary IDLE means durable actionable count zero, no in-flight, no dirty critical state, no due retries, no pending manual repair, initial reconciliation complete; not merely transfer count=0. 
- BOOT/RECOVERING: one startup inventory and durable intent validation; incremental bounded reads; no duplicated worker process. 
- IDLE: no continuous full download/MP4/DB/inventory polling; zero periodic optional metadata/size/network, no FFmpeg, no progress UI callbacks for hidden screen; one cheap observer or Android scheduled future when due. Preserve OS notification jobs and lazy runtime pools; no forcibly killing process, closing live Room, clearing caches or forced GC. 
- RUNNABLE: shared scheduler drains dirty IDs, native ready/candidate deadlines, bounded queues, no wait inside worker on subtitle/server dependency. 
- WAITING: persisted reason and earliest monotonic deadline; park worker until event / network available / service READY / subtitle receipt / storage / explicit request. Use backoff+jitter; if no future event reliable schedule low-frequency single retry. For system time change/restart reconstruct persisted wall retry deadlines conservatively. 
- ACTIVE: sample in-flight bytes/mux progress, not scan all historical items; immediate critical completion receipt and same-key wake. Finish active tasks before reducing concurrency when pressured.
- DRAINING: last-job transition atomic under coordinator; recheck dirty epoch/event sequence before scheduling idle; flush durable critical states; optional backup debounce, then sleep. 
Wake reasons: new accepted intent, connected callback, native progress/terminal, verified subtitle, scoped work-file observer, retry deadline, process startup/reentry, user manual repair, storage/network conditions. Guard races: event arrives while scan running or between empty check and park; event sequence/dirty counter + single scheduled task; startup reconciliation recovers missed events; persistent ledger is truth and logs not a queue. Force-stop by Android intentionally stops until manual reopen.
